### 태블릿 측정 (S1 장면, 2026-10-18, 기준 기기 A, 사용자 보고)

화면 주사율 120 Hz, `vsync=1`(수직동기 켜짐: 코드의 해제 요청이 안드로이드에서는 적용되지 않음). 그래서 프레임 시간은 화면 주기(8.33 ms)의 배수로 묶인다.

| 반대편 건물 수 | 단순화 끔 (평균 / draw call) | 단순화 켬 (평균 / draw call) |
|---|---|---|
| 512 | 8.81 ms / 1,069 | 8.91 ms / 557 |
| 2,048 | 8.85 ms / 4,143 | 8.92 ms / 2,095 |
| 8,192 | 24.0 ms / 16,429 | 15.0 ms / 8,237 |

### MultiMesh 비교 (x16 = 건물 8,192개, 2026-10-18, 기준 기기 A, 사용자 보고)

| 방식 | 프레임 평균 | 렌더 CPU | 렌더 GPU | draw call |
|---|---|---|---|---|
| 노드, 단순화 끔 | 20.7 ms | 9.23 ms | 11.66 ms | 16,432 |
| 노드, 단순화 켬 | 12.7 ms | 4.77 ms | 7.66 ms | 8,240 |
| MultiMesh, 단순화 끔 | 8.3 ms | 0.41 ms | 3.36 ms | 52 |
| MultiMesh, 단순화 켬 | 8.3 ms | 0.38 ms | 2.96 ms | 52 |

해석(추정): 노드 방식에서 CPU+GPU 시간의 합(20.9, 12.4 ms)이 프레임 평균(20.7, 12.7 ms)과 거의 같아서 이 렌더러·기기에서는 CPU와 GPU 작업이 겹치지 않고 이어진다고 본다(점 두 개 기준, 확정 아님). MultiMesh는 draw call 316분의 1, CPU 22분의 1, GPU 3.5분의 1이며 프레임 시간이 화면 주기(8.33 ms)에 닿는다. 측정마다 오차가 있다(같은 조건에서 이전 24.0 ms, 이번 20.7 ms).

앞의 첫 측정(노드 방식) 해석: 512와 2,048개는 한 주기 안에 끝나지만 여유는 알 수 없다. 8,192개에서 처음 한계가 드러난다(약 41 FPS, 단순화하면 약 66 FPS). 병목은 draw call로 보이며 호출당 약 1.5~1.8 µs(점 두 개로 계산한 근사). 거리 단순화는 부하가 클 때 효과가 있다. 이 해석을 확인하려고 MultiMesh 비교와 수직동기와 무관한 CPU 렌더 시간 표시를 추가해 측정했다(아래 표와 D19).

**아직 닫히지 않은 위험:** (1) 모바일 GPU 셰이더 정밀도(미측정), (2) 조명·그림자·복잡한 메시를 넣은 실제 장면의 비용, (3) 중급 기기에서의 성능, (4) 터치 조작 설계.
