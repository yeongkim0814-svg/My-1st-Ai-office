# Codex

## 강점
초기 가설이며 관찰 기록으로 갱신한다.

- 범위가 분명한 구현 Issue를 독립적으로 수행하는 것 (Issue #6 시험에서 확인).
- 규약 준수와 보고의 정직성 (Issue #6 시험에서 확인: 실패와 대체 수단을 숨기지 않고 보고).
- PR 리뷰: `@codex review` (PR #5에서 확인).

## 맡기지 말 일
- 자기가 쓴 PR의 검토 (자기 검토 금지).
- 규약 파일(`docs/protocol/`, `agents/`, `.github/`, 진입 파일) 수정. 허점은 Issue로 제안한다.
- 병합.

## 쓰기 허용 경로
Issue가 선언한 경로뿐이다.

## 브랜치 접두어
`codex/` → `codex/<이슈번호>-슬러그`

## 기동 방법
**구현 (Codex 채팅에서 직접 요청)**
ChatGPT의 Codex 채팅에 레포 URL과 Issue 수행 요청을 입력한다. 요청문에는 아래 세 가지를 반드시 넣는다.

> https://github.com/<소유자>/<레포> 레포의 Issue #N을 수행해 줘. 먼저 AGENTS.md를 읽고 Issue가 선언한 경로만 수정해. 변경은 `codex/N-슬러그` 브랜치로 GitHub에 푸시하고 `main` 대상 PR을 **실제로 열어** 줘. 본문에 `Closes #N`을 넣고 PR URL을 알려줘. PR을 열지 못했다면 열지 못했다고 분명히 말해 줘.

- Codex 보고에 따르면 채팅에 연결된 관리형 클라우드 실행 환경에서 파일 수정과 로컬 검증을 하고, `git push`가 프록시 오류로 실패하면 GitHub 연결 도구(API)로 브랜치와 커밋을 게시해 PR을 만든다(Issue #6).
- "PR 메타데이터를 생성했다"는 표현은 PR이 열렸다는 뜻이 **아니다.** 반드시 PR URL을 받고, 지휘자는 GitHub에서 PR이 실제로 있는지 확인한다.

**리뷰**
PR에 댓글로 `@codex review`. 동작 확인됨(PR #5).

**GitHub 댓글(`@codex …`)로 작업 기동 — 구현에는 쓰지 않는다**
작업은 실행되지만 결과를 GitHub에 올리지 못한다. 실행 환경에 원격(`origin`)이 없고 PR 생성 버튼도 없었다(Issue #6, 같은 계정·같은 권한). 댓글 기동은 legacy 방식의 클라우드 환경이 있어야 반응했다는 시각 순서상의 정황이 있으나 확정은 아니다.

**화면 위치**
- 사용자가 제공한 대화 주소의 형식은 `https://chatgpt.com/local/<대화 ID>`이다. 대화마다 다른 비공개 링크이므로(이 레포는 공개 레포다) 개별 주소는 레포에 적지 않는다.
- 주소 경로의 `local`이 무엇을 뜻하는지, 사용한 화면의 메뉴 이름, legacy/새 방식 구분은 **미확인**이다. Codex가 세션 정보에 없다고 밝혔다. 사용자가 확인해 이 항목을 채운다.

## 알려진 특성 (2026-10-15 시험 — Issue #6, PR #7)
1. **결과를 GitHub에 올리지 못하는 경로가 있다.** 댓글 기동 작업이 그렇다. 채팅에서 "PR을 실제로 열어 달라"고 요청한 경우에만 PR이 열렸다.
2. **보고가 모호할 수 있다.** 댓글 기동 작업은 "PR 메타데이터를 생성했다"고만 보고해 실제 PR이 없었다. PR URL을 요구하고 직접 확인한다.
3. **실행 환경에 원격 참조가 없다.** `origin/main`을 쓰는 검증 명령이 실패한다. Codex는 실패를 숨기지 않고 기준 커밋 비교로 대체하고 그 사실을 보고했다(`docs/protocol/handoff.md` "검증 명령 대체").
4. **커밋 작성자가 사용자 계정으로 찍힌다.** API로 게시하기 때문이다. 어떤 에이전트가 썼는지는 브랜치 접두어와 PR 본문으로 판단한다(`docs/protocol/handoff.md` "커밋 작성자").
5. 착수 댓글과 `status:*` 라벨 변경은 하지 않는다. 상태 라벨은 지휘자가 바꾼다.
6. 컨테이너가 일회용이라 같은 Issue를 다시 요청하면 처음부터 다시 작업한다.
