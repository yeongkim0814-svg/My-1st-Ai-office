# 멀티 에이전트 공동 작업 공간 설계

- 날짜: 2026-10-15
- 상태: 설계 확정(구두 승인), 문서 검토 대기
- 범위: 레포 구조, 작업 수명주기, 역할·충돌 규칙, 자동화 확장 경로

## 1. 목표와 성공 기준

**목표**: 이 레포를 Claude, Codex, Gemini(Jules) 및 추후 추가될 에이전트의 공동 작업 공간으로 만든다. Claude가 지휘하고, 구현과 리팩터링도 가능한 범위에서 맡는다.

**제약**: 운영자는 태블릿 환경이다. 데스크톱 앱 없이 GitHub(웹/앱)과 각 에이전트의 웹 UI만으로 돌아가야 한다.

**성공 기준**
- 태블릿에서 Issue 하나를 쓰고 담당 에이전트를 지정하면, 그 에이전트가 PR로 결과를 내고 Claude가 검토할 수 있다.
- 새 에이전트는 진입 파일 1개, 역할 정의 1개, 라벨 1개 추가만으로 합류한다. 규약 본문은 바뀌지 않는다.
- 모든 변경은 PR을 거치고, 병합은 사용자가 한다.

**확정된 가정**
- 소통 채널은 GitHub Issue·PR·라벨과 레포 안 파일뿐이다. 별도 서버는 두지 않는다.
- 초기에는 에이전트를 사용자가 수동으로 띄운다(A단계). 자동화는 필요가 확인된 뒤 붙인다(B단계).
- 레포 공개 여부는 미확정이다. 보안 규칙(§8)은 공개 레포를 가정한 엄격한 기준으로 쓴다.

## 2. 레포 구조

```
.
├── AGENTS.md              공통 규약 진입점 (Codex 등이 읽음)
├── CLAUDE.md              지휘자 진입점
├── GEMINI.md              Gemini 진입점
├── .github/
│   ├── ISSUE_TEMPLATE/task.yml
│   ├── pull_request_template.md
│   └── labels.yml
├── docs/
│   ├── protocol/          규약 원본 (single source of truth)
│   │   ├── README.md      전체 흐름 한 장 요약
│   │   ├── lifecycle.md   수명주기 (§4)
│   │   ├── handoff.md     보고·인수인계 형식
│   │   └── conflicts.md   충돌 방지 (§6)
│   ├── decisions/         구조 변경 기록 (ADR)
│   └── superpowers/specs/ 설계 문서
├── agents/
│   ├── _template.md
│   ├── claude.md
│   ├── codex.md
│   └── gemini.md
└── projects/              실제 산출물, 프로젝트별 폴더
    └── <project-name>/
```

**원칙**
- 규약은 `docs/protocol/`에만 쓴다. 진입 파일 3종은 10~20줄로 유지하고 "① `docs/protocol/README.md`를 먼저 읽는다 ② 자기 역할은 `agents/<이름>.md` ③ 작업은 Issue에서 시작한다"만 말한다. 규약 복붙은 금지한다(낡은 사본이 에이전트마다 다른 규칙을 만들기 때문).
- 진입 파일 본문은 특정 임포트 문법에 의존하지 않는 일반 문장으로 쓴다. 자동 로딩이 없는 환경에서도 "먼저 `AGENTS.md`를 읽어라"라는 지시로 같은 규약에 도달해야 한다.
- 규약 파일과 산출물은 폴더로 분리한다.

**`agents/<이름>.md` 항목**: 강점(초기 가설), 맡기지 말 일, 쓰기 허용 경로, 브랜치 접두어, 기동 방법(사람이 띄우는 법), 관찰 기록.

**새 에이전트 추가**: `agents/_template.md` 복사·작성 → 얇은 진입 파일 → 라벨 `agent:<이름>` → 브랜치 접두어 결정.

## 3. 역할

| 에이전트 | 역할 | 권한 |
|---|---|---|
| Claude | 지휘(Issue 분해·배정, PR 검토, 규약 관리) + 구현(코딩, 리팩터링) | Issue가 선언한 경로 안에서 수정, 규약 파일은 해당 Issue로만 수정 제안 |
| Codex, Gemini(Jules), 신규 | 배정된 Issue 수행 | Issue가 선언한 경로 안에서만 수정 |
| 사용자 | Issue 작성, 에이전트 기동(A단계), 병합 | 전권 |

**Claude의 두 모드**
- **지휘**: 항상 먼저 처리한다. 검토 대기열이 구현 때문에 밀리면 안 된다.
- **구현**: `agent:claude` Issue를 수행한다. 지휘 대기열이 비었을 때 진행한다. 다른 에이전트와 같은 수명주기(§4)와 규칙(§6)을 따른다.

**강점은 가설이다.** 각 `agents/*.md`에 "관찰 기록"을 두고, PR을 검토할 때마다 규약 준수, 범위 이탈, 검증의 정직성을 한 줄씩 남긴다. 배정 기준은 이 기록으로 갱신한다.

## 4. 작업 수명주기

```
Issue 작성 → 배정 → 착수 → 작업 → PR 보고 → 검토 → 병합(사용자)
```

**상태**는 라벨 `status:*` 하나로만 표시한다: `ready` → `in-progress` → `review` → `changes-requested` → `done`, 그리고 어느 단계에서든 `blocked`.

1. **작성**: 사용자(또는 Claude)가 Issue 템플릿으로 쓴다. 필수 항목: 목표 / `type`(feature·refactor·fix·docs) / 규모(S·M·L) / 예산 메모 / 수정 가능 경로(한 줄에 경로 하나) / 완료 조건 / 검증 방법 / 선행 작업(`depends on #N`). Claude가 큰 목표를 하위 Issue로 분해한다.
2. **배정**: Claude가 `agent:*` 라벨을 붙이고 경로 겹침을 검사한 뒤 `status:ready`로 바꾼다.
3. **착수**: A단계에서는 사용자가 에이전트를 띄우며 표준 지시문을 준다 — "`AGENTS.md`를 읽고 Issue #N을 수행하라." 에이전트는 Issue에 착수 댓글을 달고, `<에이전트>/<이슈번호>-슬러그` 브랜치를 만들고, 상태를 `in-progress`로 바꾼다.
4. **작업**: 선언된 경로 안에서만 수정한다. 막히거나 범위를 넘어야 하면 작업을 멈추고 Issue에 질문하며 `status:blocked`로 바꾼다. 임의로 확장하지 않는다.
5. **보고**: `Closes #N`이 들어간 PR을 연다. 양식: 요약 / 변경 파일 / 검증 결과(실행한 명령과 실제 출력) / 가정과 미해결 사항.
6. **검토**: 작성자와 검토자는 다르다. Claude 외 에이전트의 PR은 Claude가, Claude의 PR은 다른 에이전트(또는 Gemini Code Assist 같은 자동 리뷰 앱)가 1차 검토하고, 완료 조건 기준으로 판정한다. 검증 결과가 "확인했다"뿐이면 반려한다.
7. **병합**: 모든 변경은 PR을 거치고 병합은 사용자만 한다. main 직접 push는 막는다(브랜치 보호). 신뢰가 쌓이면 `projects/` 아래 저위험 작업에 한해 직접 push 허용(`lane:direct`)을 별도 결정(ADR)으로 검토한다.

**Claude의 기동 방식**: Issue 생성만으로는 깨어나지 않는다. 사용자가 세션을 열어 시작한다. PR에 활동 구독(`subscribe_pr_activity`)을 걸면 리뷰·CI 이벤트로 세션이 깨어난다.

## 5. 토큰·컨텍스트 관리

세 층으로 나눈다.

1. **컨텍스트 위생**: 진입 파일은 짧게 유지한다. Issue는 그것만 읽고 작업할 수 있는 자기완결형으로 쓴다. 세션이 끊겨도 Issue 댓글의 인수인계 메모(`handoff.md` 형식)로 이어간다.
2. **사용량 예산**: Issue의 규모와 예산 메모로 관리한다. 한 Issue가 한 세션 안에 끝나는 크기가 되도록 Claude가 분해한다. 에이전트별 실사용 관찰은 관찰 기록에 남긴다.
3. **API 비용**(B3 이후): 키별 사용 한도를 설정하고 규약에 명시한다.

**선택 사항(초기에는 꺼 둠)**: 지휘 세션을 가볍게 유지하고 구현 Issue마다 별도 작업 세션을 띄우는 방식. 필요해지면 `agents/claude.md`에 규칙으로 추가한다.

## 6. 충돌 방지 규칙

1. **경로 선언제**: Issue의 "수정 가능 경로"가 겹치는 열린 Issue는 동시에 `in-progress`가 될 수 없다. 배정 시 Claude가 검사하고, PR 검토 때 변경 파일이 선언 경로를 벗어났는지 한 번 더 확인한다.
2. **브랜치 격리와 main 보호**: 작업은 에이전트별 브랜치와 PR로만 들어온다.
3. **보호 경로**: `docs/protocol/`, `agents/`, `.github/`, 진입 파일 3종은 그것을 목표로 하는 Issue로만 수정한다. 에이전트는 작업 중 발견한 규약의 허점을 직접 고치지 않고 Issue로 제안한다.
4. **공유 파일**(락 파일·설정·인덱스): 단일 Issue 담당으로 둔다.
5. **의존성**: `depends on #N`이 `done`이 되기 전에는 착수하지 않는다.
6. **동시 작업 상한**: 에이전트당 `in-progress` Issue는 1개.
7. **충돌 해결**: 나중에 병합하는 쪽이 base 브랜치를 자기 브랜치에 병합해 해결한다. 공유된 브랜치에 rebase·force push를 하지 않는다.
8. **검증의 정직성**: PR의 검증 결과에는 실행한 명령과 실제 출력을 적는다. 실행하지 못한 것은 "미실행"으로 적는다.
9. **비밀정보 금지**: 키·토큰을 커밋하지 않는다.
10. **리팩터링 독점 잠금**: `type:refactor` Issue는 경로가 겹치는 다른 `in-progress` Issue가 없을 때만 착수하고, 진행 중에는 그 경로의 새 착수를 막는다. 목표는 동작 보존이며, 전후에 같은 검증 명령을 돌린 출력을 PR에 첨부한다. 큰 구조 변경은 단계별 Issue로 쪼갠다.
11. **자기 검토 금지**: 어떤 에이전트도 자기 PR을 검토하지 않는다(Claude 포함).

## 7. 에이전트별 연결

| 에이전트 | A단계(수동) | B단계(자동) |
|---|---|---|
| Gemini | Jules 웹 앱에서 레포 연결, 표준 지시문으로 작업 지시. Gemini Code Assist GitHub 앱을 보조 리뷰어로 설치(댓글 `/gemini review`로 수동 호출 가능). | `run-gemini-cli` GitHub Action — Issue/PR 댓글의 `@gemini-cli` 멘션 |
| Codex | 웹/클라우드에서 레포 연결, 표준 지시문으로 작업 지시 | GitHub 댓글 호출 연동(도입 전에 현재 공식 문서로 검증 필요) |
| Claude | 사용자가 세션을 열어 시작. PR 구독으로 검토 이벤트 수신 | Claude Code GitHub Action(`@claude` 멘션), 비용 발생 |

Jules의 태블릿 브라우저 동작과 `AGENTS.md` 로딩 여부, 작업 시작 전 계획 확인 단계의 존재는 이 문서 작성 시점에 미확인이다. 첫 시험(§9)에서 확인한다.

## 8. 자동화 확장 경로 (B단계)

원칙: 수동으로 불편이 확인된 곳만 자동화한다. 각 단계는 독립적이며 규약(§2~§6)은 바뀌지 않는다.

| 단계 | 내용 | 필요한 것 |
|---|---|---|
| B1 규약 검사 | PR 오픈 시 Actions가 ① 변경 파일이 Issue의 수정 가능 경로 안인가 ② 브랜치명·PR 양식 필수 항목 ③ 보호 경로 변경 여부를 검사 | 시크릿 없음 |
| B2 상태 자동화 | PR 열림 → `status:review`, 병합 → `done`. `labels.yml` 동기화 | 시크릿 없음 |
| B3 Gemini 기동 | `run-gemini-cli` | Gemini API 키 |
| B4 Codex 기동 | 공식 연동(검증 후) | 계정 연동 |
| B5 Claude 기동 | Claude Code GitHub Action | API 키, 비용 |

**추천 순서**: B1 → B2 → 필요 시 B3/B4 → B5.

**자동 기동 보안 규칙(B3 이후 필수, 공개 레포 가정)**
- 레포 소유자·협업자의 멘션에만 반응한다(`author_association` 검사).
- 워크플로 `permissions`는 최소로 준다(`contents: write`, `pull-requests: write`까지).
- 시크릿은 포크 PR에 노출하지 않는다.
- API 사용 한도를 설정한다.
- Issue·댓글 텍스트는 신뢰할 수 없는 입력으로 취급한다(프롬프트 인젝션 대비).

B1의 경로 검사는 Issue 본문의 "수정 가능 경로" 칸을 파싱하므로, 템플릿에서 해당 칸을 "한 줄에 경로 하나" 형식으로 고정한다.

## 9. 첫 시험과 검증

**구축 순서**
1. 스캐폴드(§2의 파일 전체)를 PR로 올리고 사용자가 병합해 main을 만든다. 레포가 비어 있어서 기준 브랜치가 필요하다.
2. 라벨을 생성한다(`agent:*`, `status:*`, `type:*`, `blocked`).
3. 브랜치 보호(main 직접 push 금지)를 설정한다. 태블릿에서 GitHub 웹 설정 화면으로 한다.
4. Jules smoke test.

**Jules smoke test**: Issue "`projects/_smoke/hello-jules.md`에 한 줄 작성"을 Jules에 준다. 관찰 항목:
- `AGENTS.md`를 읽었는가
- 지정 형식의 브랜치명을 썼는가
- PR 양식을 채웠는가
- 수정 가능 경로 밖을 건드리지 않았는가
- 작업 시작 전 계획 확인 단계가 있는가(있다면 경로 확인에 활용)

결과는 `agents/gemini.md` 관찰 기록과 필요 시 ADR에 반영한다. Codex에도 같은 시험을 수행한다.

**알려진 취약점**
- 에이전트가 진입 파일을 읽지 않으면 §6 전체가 무력해진다. Issue 템플릿과 표준 지시문에 핵심 규칙(브랜치명, 보고 형식, 경로 제한)을 중복해 이중으로 막는다.
- 경로 겹침 검사는 B1 전까지 Claude의 수동 확인에 의존한다.
- 에이전트가 3개를 넘으면 `agents/`가 비대해질 수 있다. 현재는 다루지 않는다.

## 10. 범위 밖 (YAGNI)

- 별도 서버·대시보드·데이터베이스
- 에이전트 간 직접 통신 (모든 소통은 Issue·PR을 거친다)
- 지휘 세션과 작업 세션의 자동 분리 (§5 선택 사항)
- `lane:direct` 직접 push (신뢰가 쌓인 뒤 별도 결정)
- `projects/` 내부의 언어·빌드 규칙 (프로젝트가 생길 때 각자 정의)
